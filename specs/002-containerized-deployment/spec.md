# Feature Specification: 容器化部署与镜像交付

**Feature Branch**: `main`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "后端和前端支持以 Docker 容器化运行，同时在 GitHub Actions 工作流中添加构建 image 的流程。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一条命令启动完整系统 (Priority: P1)

部署人员可以通过一个编排命令启动后端、前端和持久化数据目录，不需要在宿主机安装 Go 或 Node.js。

**Why this priority**: 容器化的首要价值是提供一致、可重复的运行环境，并降低部署门槛。

**Independent Test**: 在只安装容器运行时的干净环境中配置管理员令牌后启动系统，确认前端可访问、后端健康、机器人 mock 模式可操作。

**Acceptance Scenarios**:

1. **Given** 已安装兼容的容器运行时，**When** 部署人员提供必需配置并执行启动命令，**Then** 前后端均进入健康状态且管理台可访问。
2. **Given** 系统已经写入群、消息和审计数据，**When** 容器被重建后重新启动，**Then** 持久化数据仍可查询。
3. **Given** 后端尚未健康，**When** 前端容器启动，**Then** 系统不会把整体服务错误标记为完全可用。

---

### User Story 2 - 安全配置容器运行参数 (Priority: P1)

部署人员通过外部配置提供管理员令牌、机器人驱动和可选的 Wechaty 服务令牌，镜像本身不包含环境秘密。

**Why this priority**: 容器镜像通常会被共享和缓存，任何内置秘密都会形成高风险泄露。

**Independent Test**: 构建镜像并检查镜像配置和文件内容，确认示例值存在但真实运行令牌不在镜像层中；缺少必填令牌时后端明确拒绝启动。

**Acceptance Scenarios**:

1. **Given** 未提供管理员令牌，**When** 启动后端容器，**Then** 后端以非零状态退出并给出非敏感配置错误。
2. **Given** 提供 mock 驱动和管理员令牌，**When** 启动系统，**Then** 不需要 Wechaty 服务令牌即可运行。
3. **Given** 选择真实 Wechaty 驱动但未提供服务令牌，**When** 启动后端，**Then** 后端拒绝启动且日志不打印任何已有秘密。

---

### User Story 3 - 自动验证并交付镜像 (Priority: P2)

维护人员提交 Pull Request 时，自动化流程构建前后端镜像验证 Dockerfile；合并到主分支后，自动生成可从项目容器仓库获取的镜像。

**Why this priority**: 自动构建防止容器定义与源码漂移，并让主分支始终对应可部署制品。

**Independent Test**: 在 Pull Request 中修改容器或应用文件，确认两个镜像都成功构建但不发布；合并主分支后确认两个镜像带有可追踪标签并发布。

**Acceptance Scenarios**:

1. **Given** 针对主分支的 Pull Request，**When** 镜像工作流运行，**Then** 前后端镜像都必须成功构建且不会推送到容器仓库。
2. **Given** 代码提交到主分支，**When** 镜像工作流成功，**Then** 前后端镜像被发布并带有主分支、提交摘要和最新稳定标签。
3. **Given** 任一镜像无法构建，**When** 工作流运行，**Then** 工作流失败且不会将失败镜像标记为可部署版本。

---

### User Story 4 - 通过同源入口使用管理台 (Priority: P2)

管理员只访问前端服务地址，管理台在不暴露内部容器网络结构的情况下调用后端 API 和实时事件流。

**Why this priority**: 同源入口简化部署、防止浏览器使用容器内部主机名，并减少跨域配置错误。

**Independent Test**: 仅公开前端端口，通过浏览器完成登录、绑定、群查询和消息操作，确认 API 与事件流均正常。

**Acceptance Scenarios**:

1. **Given** 前后端运行在内部容器网络，**When** 浏览器请求管理 API，**Then** 请求通过公开入口转发到后端。
2. **Given** 管理台订阅实时事件，**When** 后端发送状态或消息事件，**Then** 事件持续传输且不被代理缓冲。
3. **Given** 用户刷新任意前端路径，**When** 静态服务器找不到物理文件，**Then** 返回应用入口而不是 404。

### Edge Cases

- 宿主机端口被占用时，启动必须失败并提供可配置端口方案。
- 后端容器重启时，前端静态页面仍可加载，但 API 操作应显示明确失败并在后端恢复后重新可用。
- 持久化目录无写权限时，后端必须启动失败而不是静默使用临时数据。
- 容器收到终止信号时，后端必须有机会完成现有优雅关闭流程。
- 实时事件连接经过反向代理时不得被响应缓冲或过早超时。
- Pull Request 来自分叉仓库时，不得尝试使用写权限发布镜像。
- 同一分支的旧镜像构建应在新提交到达后取消，避免发布过期制品。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供可独立构建的后端运行制品定义。
- **FR-002**: 系统必须提供可独立构建的前端运行制品定义。
- **FR-003**: 两个运行制品必须使用分阶段构建，最终制品不得包含完整源码、编译缓存或开发依赖。
- **FR-004**: 最终运行进程必须使用非 root 身份。
- **FR-005**: 系统必须提供一个编排定义，用于启动前端、后端和持久化存储。
- **FR-006**: 编排定义必须支持通过环境变量配置公开端口、管理员令牌、机器人驱动和可选服务令牌。
- **FR-007**: 后端业务数据必须存储在独立于容器生命周期的持久化卷中。
- **FR-008**: 前后端运行制品必须提供可用于编排和自动化检查的健康状态。
- **FR-009**: 前端公开入口必须把管理 API、健康检查和实时事件请求转发给后端。
- **FR-010**: 前端构建默认必须使用同源后端地址，同时保留开发环境覆盖能力。
- **FR-011**: 镜像和编排构建上下文必须排除本地依赖、环境文件、数据库、测试输出和版本控制元数据。
- **FR-012**: 自动化流程必须在 Pull Request 和主分支提交时构建前后端镜像。
- **FR-013**: Pull Request 运行不得向容器仓库推送镜像。
- **FR-014**: 主分支成功构建后必须发布前后端镜像到项目容器仓库。
- **FR-015**: 发布镜像必须包含可追踪到分支和源代码提交的标签与元数据。
- **FR-016**: 自动化流程必须使用最小权限，并仅在需要发布时申请包写权限。
- **FR-017**: 自动化使用的外部构建动作必须固定到不可变版本引用。
- **FR-018**: 容器化运行说明必须覆盖首次配置、启动、停止、查看日志、升级和真实 Wechaty 模式。

### Key Entities

- **Backend Image**: 包含可执行后端服务、运行用户、健康检查和默认非敏感配置的不可变制品。
- **Frontend Image**: 包含静态管理台和同源反向代理配置的不可变制品。
- **Application Stack**: 前端、后端、内部网络和持久化卷组成的一次部署实例。
- **Image Build**: 针对一个源代码提交执行的前后端镜像构建结果，包含状态、标签和源代码关联信息。
- **Published Image**: 成功推送到项目容器仓库、可供部署拉取的镜像版本。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新部署人员可在 10 分钟内完成配置并用一个命令启动完整 mock 系统。
- **SC-002**: 容器重建后，100% 的既有 SQLite 业务数据仍可查询。
- **SC-003**: 前端公开入口启动后 60 秒内，前端和后端健康检查均通过。
- **SC-004**: 浏览器仅通过一个公开端口即可完成现有绑定、群管理、消息和审计流程。
- **SC-005**: 每个 Pull Request 都会验证两个镜像可构建，失败时阻止镜像工作流通过。
- **SC-006**: 主分支成功构建后，两个镜像均在 15 分钟内出现在项目容器仓库，并可追踪到确切提交。
- **SC-007**: 镜像内容和自动化日志的秘密扫描不发现管理员令牌或 Wechaty 服务令牌。
- **SC-008**: 最终前后端镜像均不以 root 用户运行。

## Assumptions

- 容器运行环境支持 Docker Compose v2 或兼容的 Compose Specification。
- 项目容器仓库使用与源码仓库关联的 GitHub Container Registry。
- 主分支发布 `main`、提交摘要和 `latest` 标签；Pull Request 仅构建验证。
- 首版构建 Linux AMD64 镜像，不承诺多架构发布。
- TLS 由生产环境上游入口或负载均衡器终止，项目内前端容器提供 HTTP 服务。
- SQLite 继续作为单实例持久化存储；同一个数据卷不会被多个后端副本同时写入。
